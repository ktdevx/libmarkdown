# libmarkdown タスクリスト

## 1. 目的

本書は、[要件定義書](requirements.md) と [設計書](design.md) を、実装可能な作業単位へ分解したものである。各タスクは、対応する要件、変更対象、検証方法を明示し、実装順序と依存関係が追跡できるようにする。

本書は実装計画の正本であり、個別の実装 PR は原則としてここに記載されたタスクのいずれかに対応させる。

## 2. 分解方針

- タスクは、単独で設計判断を再発明しない粒度に分ける。
- 先行しなければ後続タスクの実装が定まらない基盤作業を先に置く。
- 解析、AST 基本構造、属性、編集、シリアライズ、アロケータ、テスト、文書を別々に追跡できるようにする。
- 公開 API を変更するタスクでは、対応する man ページと API 索引更新も同じタスクまたは直後のタスクに含める。

## 3. タスク一覧

### T1. 公開契約と基盤型を整備する

- 対応要件: FR-2, FR-4, NFR-2, NFR-3, VR-3
- 対応設計: 3.1, 3.2, 3.3, 4, 公開 API の共通規則
- 変更対象: 公開型、列挙値、状態コード、診断型、アロケータ関連の共通宣言、API 索引
- 内容:
  - 公開 AST と診断、状態コード、列挙値、定数の土台を確定する。
  - 公開 API で共通に使う文字列、所有権、失敗時の戻り値、診断引数の規則を実装に落とす。
  - man3 の公開型ページが必要なシンボル群を整理し、API 索引と整合させる。
- 検証方法:
  - 公開ヘッダと API 設計書の宣言が一致していることを確認する。
  - 新規または更新した man ページの `SYNOPSIS` が公開ヘッダと一致することを確認する。
  - `git diff --check` を確認する。
- 依存関係: なし

### T2. AST ノードの生成・破棄を実装する

- 対応要件: FR-2, NFR-3, VR-3
- 対応設計: 3.3, 4
- 変更対象: ノード生成、破棄、document ルート、フラグメントの所有権処理
- 内容:
  - document と通常ノードの生成、破棄、および所有権の基本動作を実装する。
  - 切り離しフラグメントと接続済み木の寿命を、設計書の契約に一致させる。
  - 破棄時の原子性と再試行可能性を満たすようにする。
- 検証方法:
  - 生成、破棄、切り離し後の所有権が変化する条件を確認する。
  - 空文書と深いネストの境界ケースを確認する。
- 依存関係: T1

### T3. 親子関係の編集を実装する

- 対応要件: FR-2, VR-2, VR-3
- 対応設計: 3.2, 3.3
- 変更対象: `md_node_insert_before()`、`md_node_detach()`、親子関係の検証、失敗時非変更
- 内容:
  - 親子関係の接続、切り離し、単一親制約、循環なし、共有なしを実装する。
  - `list`、`list_item`、`block_quote`、`paragraph`、`emphasis`、`strong` の最小子数契約を実装する。
  - 失敗時にノード、所有権、親子関係を変更しない原子性を確保する。
- 検証方法:
  - 不正な接続と切り離しが `MD_INVALID_AST` を返し、状態を変えないことを確認する。
  - 移動と切り離しの後に AST 正規形が安定することを確認する。
- 依存関係: T2

### T4. ノード属性 API を実装する

- 対応要件: FR-2, FR-3, NFR-2, VR-2, VR-3
- 対応設計: 3.1, 3.4, 3.5, 公開 API リファレンス
- 変更対象: literal、heading、list、link、image、reference_definition、code_block info string の getter/setter
- 内容:
  - 各ノード種別固有の属性を専用 API で操作できるようにする。
  - ordered list の開始番号、delimiter、tight/loose の契約を実装する。
  - image の alt を子ノードで表現する契約に沿って、属性 API と編集 API を分離する。
- 検証方法:
  - 1 と 999999999 の受理、範囲外の拒否を確認する。
  - bullet list の delimiter 制約、heading レベル、link/image/reference_definition の属性保持を確認する。
- 依存関係: T2, T3

### T5. Markdown 解析を実装する

- 対応要件: FR-1, FR-2, FR-5, VR-1, VR-2, VR-4
- 対応設計: 2, 3.1, 3.2, 3.4, 6
- 変更対象: Markdown 解析器、CommonMark 準拠のブロック・インライン構築、参照定義の解決
- 内容:
  - UTF-8 Markdown を AST に変換する解析処理を実装する。
  - 参照定義の収集、解決順、未解決参照の扱いを設計書どおりに実装する。
  - HTML 出力やファイル I/O を含めない。
- 検証方法:
  - CommonMark フィクスチャで期待 HTML との比較が通ることを確認する。
  - 参照定義、空文書、改行形式、深いネストの境界を確認する。
- 依存関係: T2, T3, T4

### T6. Markdown シリアライズを実装する

- 対応要件: FR-3, NFR-2, NFR-3, VR-2, VR-3
- 対応設計: 5, 5.1, 3.5
- 変更対象: AST から Markdown への出力、文脈別エスケープ、fence 選択、出力バッファ管理
- 内容:
  - 有効な AST から意味的に等価な Markdown を生成する。
  - 失敗時に AST と出力バッファを変更しない原子性を保つ。
  - image の alt、リンク、コードブロック、参照定義、改行の正規化規則を実装する。
- 検証方法:
  - 再解析後に AST 正規形が一致することを確認する。
  - 文字列、fence、エスケープ、出力寿命の境界を確認する。
- 依存関係: T2, T3, T4

### T7. グローバルアロケータ契約を実装する

- 対応要件: FR-4, NFR-3, VR-3
- 対応設計: 4, 公開 API の共通規則
- 変更対象: アロケータ設定、既存オブジェクトへの適用規則、設定失敗時の保持
- 内容:
  - 既定アロケータとカスタムアロケータの設定・復帰を実装する。
  - 既存 document、ノード、切り離しフラグメント、シリアライズ出力に対する設定変更後の挙動を実装する。
  - 不正なコールバックを含む設定を拒否し、現在設定を維持する。
- 検証方法:
  - アロケータ A から B への変更後に既存オブジェクトを操作・破棄できることを確認する。
  - 設定失敗時に現在設定が変わらないことを確認する。
- 依存関係: T1, T2, T6

### T8. AST 正規形と検証補助を実装する

- 対応要件: FR-2, FR-3, VR-2, VR-3
- 対応設計: 3.5, 5, 6
- 変更対象: テスト専用の AST 正規化、検証フック、診断補助、内部テストフック
- 内容:
  - ノード種別、子順序、意味属性、テキスト内容を比較する正規形を実装する。
  - テスト専用コードで不変条件違反 AST を構築できる補助を用意する。
  - 失敗診断を検証できるようにする。
  - `src/internal/ast_test_hooks.c` と、必要ならそれを使う内部ヘッダをテスト専用ターゲットにのみ公開する。
- 検証方法:
  - roundtrip テストで正規形が一致することを確認する。
  - 不変条件違反 AST のシリアライズ失敗と診断内容を確認する。
- 依存関係: T2, T3, T4, T6

### T9. テスト基盤を整備する

- 対応要件: VR-1, VR-2, VR-3, VR-4
- 対応設計: 2.1, 6
- 変更対象: CTest 登録、テストターゲット、ラウンドトリップテスト、API テスト
- 内容:
  - `libmarkdown_test_support`、`commonmark_conformance_test`、`roundtrip_test`、`api_test` を分離して登録する。
  - `LIBMARKDOWN_TESTING` をテスト専用ターゲットにのみ定義し、出荷ライブラリへテスト専用コードを含めない。
  - CMake の configure、build、CTest 実行が設計書どおりの構成になるようにする。
- 検証方法:
  - `ctest --output-on-failure` で各テストが独立に実行されることを確認する。
  - テスト専用コードが公開 API に漏れないことを確認する。
- 依存関係: T5, T6, T7, T8

### T10. CommonMark フィクスチャ生成と更新を管理する

- 対応要件: VR-1, VR-4
- 対応設計: 6.1
- 変更対象: `tools/extract_commonmark_examples.js`, `tests/fixtures/commonmark_0_31_2_examples.c`, 対応ヘッダ
- 内容:
  - CommonMark Spec 0.31.2 の仕様書から example を抽出して、生成済み C データを更新できるようにする。
  - 生成物に仕様バージョン、取得元 URL、著作権表示を含める。
  - 更新手順に、example 数と入力仕様書の SHA-256 を記録する要件を明記する。
- 検証方法:
  - 生成データがテスト専用ターゲットだけにリンクされ、出荷ライブラリに含まれないことを確認する。
  - オフラインの configure、build、test で CommonMark 適合性テストが実行できることを確認する。
- 依存関係: T5, T9

### T11. 公開文書を同期する

- 対応要件: FR-2, FR-3, FR-4, FR-5, VR-3
- 対応設計: 5, 6, 8, ADR 全般
- 変更対象: `docs/specs/api.md`, `docs/man/man3/*.md`, 必要な ADR
- 内容:
  - 公開 API 変更に伴う API 設計書の索引更新を行う。
  - 影響する公開シンボルについて man ページを追加または更新する。
  - 設計判断が新たに固定される場合は ADR を追加する。
- 検証方法:
  - `docs/man/` から他ドキュメントへのリンクがないことを確認する。
  - `SEE ALSO` の相互リンクが有効であることを確認する。
  - Markdown エラーと相対リンクを確認する。
- 依存関係: T1, T4, T5, T6, T7

## 4. 実施順の目安

1. T1 で公開契約の土台を固める。
2. T2 と T3 で AST の所有権と編集基盤を作る。
3. T4 で属性 API を固定する。
4. T5 と T6 で解析とシリアライズを実装する。
5. T7 でアロケータ契約を実装する。
6. T8 で正規形と検証補助を整える。
7. T9 でテスト基盤を整備する。
8. T10 で CommonMark フィクスチャ更新を管理する。
9. T11 で公開文書を同期する。

## 6. 未完了条件

次のいずれかが残っている場合、本リポジトリの実装タスク分解は未完了とみなす。

- 主要要件がどのタスクにも割り当てられていない。
- タスクの受け入れ条件が検証方法まで書かれていない。
- 公開 API の変更に対して、API 設計書または man ページの更新タスクが欠けている。
- 実装順が依存関係と矛盾している。
