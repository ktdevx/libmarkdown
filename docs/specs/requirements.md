# libmarkdown 要件定義書

## 1. 目的

libmarkdown は、UTF-8 の Markdown 文字列と編集可能な AST（抽象構文木）を相互変換する C 言語ライブラリである。

本ライブラリは CommonMark に準拠し、利用者が AST を作成、走査、編集した後に Markdown へ再シリアライズできることを目的とする。

本書における CommonMark の準拠対象は、[CommonMark Spec 0.31.2](https://spec.commonmark.org/0.31.2/) とする。

## 2. 対象範囲

### 2.1 対象範囲内

- UTF-8 の Markdown 文字列を AST へ解析する機能
- AST を Markdown 文字列へシリアライズする機能
- 利用者が操作できる公開 AST
- AST ノードの生成、変更、削除、走査に必要な操作
- カスタムメモリアロケータの設定
- CMake を使用する C99 ライブラリのビルド
- CommonMark 適合性を検証する自動テスト

### 2.2 対象範囲外

- 製品公開 API としての HTML その他の形式へのレンダリング
- ファイルからの直接入力およびファイルへの直接出力
- コマンドラインインターフェース
- 個別の独自 Markdown 拡張構文
- 原文の空白、改行形式、記法選択を完全に再現するソース保持
- API の具体的な関数名、型名、ABI の固定
- 性能に関する数値目標
- CI サービスの選定

## 3. 用語

- **Markdown**: CommonMark で定義される Markdown 文書。
- **AST**: Markdown 文書の構造および意味を表す編集可能な抽象構文木。
- **有効な AST**: 本書で定義する構造的不変条件を満たす AST。構造的不変条件には、ルート、親子関係、所有関係、必須属性、UTF-8 および対応ノード種別に関する条件を含む。
- **AST 正規形**: ノード種別、子ノード順序、意味属性およびテキスト内容を決められた順序で表現した、AST 比較用の正規化表現。ソース位置、入力時の記法および正規化された改行形式は含まない。
- **解析**: Markdown 文字列から AST を構築する処理。
- **シリアライズ**: AST から Markdown 文字列を構築する処理。
- **意味的等価性**: 再解析時に同一の文書構造および意味を表すこと。ソース位置、入力時の記法、正規化された改行形式などは含まないが、コード内容、テキスト内容、インデントおよびハード改行など意味に影響する空白は含む。

## 4. 機能要件

### FR-1: Markdown 解析

1. ライブラリは UTF-8 の Markdown 文字列を入力として受け付けなければならない。
2. ライブラリは CommonMark の構文規則に従い、入力を AST へ解析しなければならない。
3. ライブラリは文字列入力を対象とし、ファイル I/O を提供してはならない。
4. 解析に失敗した場合、利用者が失敗を識別できるエラー情報を提供しなければならない。

### FR-2: 公開 AST と編集

1. AST は利用者が観察および編集できる公開データモデルでなければならない。
2. AST は CommonMark のブロック要素およびインライン要素を表現できなければならない。
3. AST はノード種別、親子関係、ノード固有の属性およびテキスト内容を保持できなければならない。
4. 利用者はノードの生成、変更、削除、親子関係の変更および走査を行えなければならない。
5. AST の生成物と編集後の AST は、ライブラリが定義する破棄操作によって解放できなければならない。
6. ライブラリは、AST の有効性を判定するため、少なくとも次の不変条件を定義しなければならない。
   - ルートは document ノードである。
   - 各ノードの親子関係は、ノード種別ごとに許可された組み合わせである。
   - 各ノードは高々1つの親を持ち、親子関係に循環およびノード共有がない。
   - 必須属性が設定され、属性値およびテキスト内容が有効な UTF-8 である。
   - 本ライブラリが対応するノード種別だけが含まれる。
7. 有効な AST は、CommonMark の意味を保持した Markdown にシリアライズ可能でなければならない。
8. 編集操作が AST の不変条件を破る場合、操作は失敗し、AST を変更してはならない。編集操作の失敗は原子的でなければならない。
9. 親子関係の変更に成功した場合、親は子の所有権を持つ。既に親を持つノードの追加は失敗し、子の切り離しに成功した場合は所有権を利用者へ移転する。親の破棄時には、その親が所有する子も破棄する。

### FR-3: Markdown シリアライズ

1. ライブラリは、有効な AST を UTF-8 の Markdown 文字列へシリアライズしなければならない。
2. シリアライズ対象の AST が不変条件を満たさない場合、シリアライズは失敗し、利用者が原因を識別できるエラー情報を提供しなければならない。この場合、AST を変更せず、部分的な出力を成功結果として返してはならない。
3. 有効な AST のシリアライズ結果を再解析した AST は、入力 AST と意味的に等価でなければならない。
4. シリアライズは入力 Markdown の字句的な完全再現を要求しない。
5. シリアライズ結果は成功時にのみ、ライブラリが確保した出力バッファとして利用者が取得できなければならない。利用者が提供する出力バッファへの直接書き込みは対象外とする。出力バッファは専用の破棄操作で解放でき、AST と同じ操作時点のグローバルアロケータ契約を使用しなければならない。

### FR-4: メモリアロケータ

1. ライブラリはメモリ確保、再確保および解放のためのカスタムメモリアロケータを受け付けなければならない。
2. カスタムメモリアロケータが設定されない場合、標準 C ライブラリの `malloc()`、`realloc()`、`free()` を使用しなければならない。
3. ライブラリは共通のグローバルアロケータ設定を保持し、AST、ノード、切り離しフラグメントおよび関連する出力バッファの各操作に、操作時点の設定を適用しなければならない。
4. アロケータ設定の変更後に既存のオブジェクトを操作する場合、設定変更前に確保されたメモリを新しいコールバックで扱えること、および設定変更とオブジェクト操作の同期は利用者が保証しなければならない。
5. カスタムアロケータは、標準アロケータへ復帰可能でなければならない。
6. 不正なコールバックを含む設定が渡された場合、設定変更は失敗し、現在の設定は変更してはならない。

### FR-5: 拡張性

1. CommonMark のみを実装対象とする。
2. パーサー、AST およびシリアライザの設計は、将来の独自 Markdown 拡張を追加できることを妨げてはならない。
3. 対応しないノード種別は入力、生成およびシリアライズ時に拒否し、将来の拡張ノード登録機構は対象外とする。
4. 独自構文の種類、構文規則、設定方法および相互運用規則は本書の対象外とし、導入時に別途定義する。

## 5. 公開 API の設計方針

公開 API は C99 から利用可能とし、少なくとも次の責務を提供する。

- Markdown 文字列を受け取り AST を返す解析操作
- AST を受け取り Markdown 文字列を返すシリアライズ操作
- AST の生成、編集、走査および破棄の操作
- アロケータの指定または既定アロケータの使用
- エラー状態および診断情報の取得

各操作の所有権、寿命、失敗時の戻り値、具体的な関数シグネチャ、公開構造体の詳細、および ABI の安定性は API 設計工程で決定する。

## 6. 非機能要件

### NFR-1: 言語と移植性

1. 実装は C99 に対応しなければならない。
2. ライブラリは Linux、Windows および macOS でビルドおよびテスト可能でなければならない。
3. ビルドシステムには CMake を使用しなければならない。

### NFR-2: 文字エンコーディング

1. API の文字列入力および出力は UTF-8 とする。
2. 解析入力、ノードのテキストおよび文字列属性、ならびにシリアライズ対象の AST は、有効な UTF-8 であることを利用者が保証しなければならない。
3. ライブラリは UTF-8 の妥当性を検証、正規化または補正してはならない。前項の前提に違反した入力に対する解析結果、シリアライズ結果、診断および文字化けは保証しない。
4. 公開 API のテキスト文字列は NULL 終端し、埋め込み NULL を含んではならない。必須の空文字列は非 NULL ポインタで表し、NULL ポインタは API が任意属性を表す場合だけ許可する。

### NFR-3: 品質

1. エラー処理は呼び出しごとに決定的でなければならない。
2. 正常系およびエラー系において、ライブラリが確保したメモリは定義された所有権に従って解放可能でなければならない。
3. アロケータの再確保が失敗した場合、元のポインタを保持し、ASTおよび出力ハンドルを変更してはならない。
4. 性能の数値目標は本書では定めず、実装のベンチマーク結果を基に後続工程で決定する。

## 7. 検証および CI/CD 要件

### VR-1: CommonMark 適合性

1. CI は CommonMark Spec 0.31.2 に収録された公式テストケースを使用する。
2. 各テストケースについて Markdown を解析し、テスト専用の HTML アダプタで AST を HTML に変換する。
3. 公式仕様書内の `example` フェンスを出現順に抽出し、各フェンス内の単独の `.` 行より前を入力 Markdown、その行より後を期待 HTML とする。仕様書内でタブを表す `→` は抽出時にタブへ戻す。
4. 生成された HTML は UTF-8 のテキストとして期待 HTML と比較し、実行環境による改行コードの差だけを LF に正規化する。その他の文字、空白および公式テストケースで定義された末尾改行は比較対象とする。
5. 比較は CommonMark が定める出力規則に従い、入力 Markdown の記法やシリアライズ形式の一致は要求しない。
6. HTML アダプタはテスト専用コードとし、公開 API および出荷ライブラリには含めない。

### VR-2: ラウンドトリップ

1. Markdown を AST に解析し、Markdown にシリアライズし、再解析する。
2. 解析前後の AST を定義済みの AST 正規形へ変換して比較する。
3. AST 正規形の比較対象はノード種別、子ノード順序、意味属性およびテキスト内容とする。意味属性には、ソフト改行/ハード改行の種別、リストの開始番号および tight/loose 状態、リンク先、参照定義、コードブロックの info string などを含む。
4. ソース位置、入力時の記法、正規化された改行形式および記法上のみ必要な空白は比較対象としない。ただし、コード内容、テキスト内容、インデントおよびハード改行など意味に影響する空白は比較対象とする。
5. 利用者が生成または編集した AST については、AST 不変条件を満たすものをラウンドトリップ検証の対象とする。

### VR-3: API 品質

CI は少なくとも次を検証しなければならない。

- AST の生成、編集、削除および走査
- 不変条件に違反する編集操作の拒否と、失敗時に AST が変更されないこと
- テスト専用コードだけで作成した不変条件違反 AST のシリアライズ失敗と診断。これらのフィクスチャは公開 API および出荷ライブラリに含めない。
- 既定アロケータとカスタムアロケータ
- アロケータAからBへの設定変更後に行う、既存 document、ノード、切り離しフラグメントおよび出力の操作・破棄
- 不正な設定の拒否、設定失敗時の現在設定の保持、および再確保失敗時の原子性
- 不正な引数および失敗時のエラー通知
- 空文書、改行形式、深いネストなどの境界条件

### VR-4: 実行環境

CI は Linux、Windows および macOS で、CMake の configure、build、test を実行しなければならない。具体的な CI サービスおよびコンパイラのバージョンは、CI 設計工程で決定する。

## 8. 受け入れ条件

本ライブラリは、次のすべてを満たした場合に受け入れ可能とする。

1. CMake により C99 ライブラリとしてビルドできる。
2. Linux、Windows、macOS の CI でビルドおよびテストが成功する。
3. CommonMark 公式テストケースについて、テスト専用 HTML アダプタを介した期待 HTML 比較が成功する。
4. UTF-8 の Markdown 文字列を AST に解析できる。
5. 利用者が AST を編集できる。
6. AST 不変条件を満たす編集後の AST を Markdown 文字列にシリアライズできる。
7. VR-2 で定義した AST 正規形の比較により、Markdown と AST の往復で意味的等価性を維持できる。
8. 既定アロケータおよびカスタムアロケータでメモリを正しく管理でき、設定変更後の既存オブジェクトも定義されたグローバル契約に従って操作・破棄できる。
9. 出荷ライブラリおよび公開 API に HTML レンダリング機能を含まない。ただし、CommonMark 適合性テスト用の非公開 HTML アダプタは除く。

## 9. 未決事項

次の事項は、本書の要件では方針のみを定め、後続工程で確認および決定する。

- 公開関数、公開型、エラーコード、戻り値の具体的な設計
- AST の詳細なノード一覧、各ノードの属性および AST 正規形の完全な仕様
- AST の編集 API における無効な操作の扱い
- CommonMark 仕様書更新時の公式テストケース差分の取り込み手順
- コンパイラの対応バージョンと警告設定
- CI サービス、依存関係の取得方法およびリリース手順
- 性能、最大入力サイズ、最大ネスト深さの目標値
- 独自 Markdown 拡張の構文と API
