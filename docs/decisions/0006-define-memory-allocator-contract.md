# AST と関連出力に生成時のメモリアロケータ契約を適用する

## Context and Problem Statement

libmarkdown は AST と Markdown 出力バッファをライブラリ内部で確保し、利用者が専用の破棄操作で解放できるようにする必要がある。標準アロケータだけを前提にすると、利用者のメモリ管理方針や組み込み環境の要件に対応できない一方、確保と解放で異なるアロケータを使用すると未定義動作やメモリ破壊につながる。

カスタムメモリアロケータをどの単位で選択し、AST とそれに関連する出力バッファの確保および解放にどのように適用するかを決定する必要がある。

## Considered Options

* 標準 C ライブラリのアロケータだけを使用する
* プロセス全体で共有するアロケータを使用する
* AST の生成時に選択したアロケータ契約を AST と関連出力に適用する

## Decision Outcome

Chosen option: "AST の生成時に選択したアロケータ契約を AST と関連出力に適用する", because AST と関連する出力バッファの所有関係および解放責任を明確にしながら、利用者がカスタムメモリアロケータを使用できるため。

カスタムアロケータが設定されない場合は、標準 C ライブラリの `malloc()`、`realloc()`、`free()` を使用する。AST の生成時に選択されたアロケータ契約は、その AST と関連する Markdown 出力バッファのメモリ確保、再確保および解放に一貫して適用する。出力バッファはライブラリが確保し、成功時に利用者へ渡し、専用の破棄操作で解放できるものとする。

### Consequences

* Good, because カスタムメモリアロケータを必要とする利用者や環境に対応できる。
* Good, because 確保と解放に同じアロケータ契約を適用し、メモリ所有権の境界を明確にできる。
* Good, because AST と関連出力バッファを同じメモリ管理方針で扱える。
* Bad, because AST および関連する出力バッファが使用するアロケータ契約を追跡して保持する必要がある。
* Bad, because 利用者は、ライブラリが確保した出力を通常の `free()` で解放せず、専用の破棄操作を使用する必要がある。
