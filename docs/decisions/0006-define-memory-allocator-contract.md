# AST と関連出力にグローバルメモリアロケータ契約を適用する

## Context and Problem Statement

libmarkdown は AST と Markdown 出力バッファをライブラリ内部で確保し、利用者が専用の破棄操作で解放できるようにする必要がある。標準アロケータだけを前提にすると、利用者のメモリ管理方針や組み込み環境の要件に対応できない一方、確保と解放で異なるアロケータを使用すると未定義動作やメモリ破壊につながる。

カスタムメモリアロケータをどの単位で選択し、AST とそれに関連する出力バッファの確保および解放にどのように適用するかを決定する必要がある。

## Considered Options

* 標準 C ライブラリのアロケータだけを使用する
* プロセス全体で共有するアロケータを使用する
* グローバルアロケータを全 document から常時参照する

## Decision Outcome

Chosen option: "グローバルアロケータを全 document から常時参照する", because 通常の公開 API を簡潔にしながら、AST、切り離しフラグメントおよび関連出力へ共通のアロケータ設定を適用できるため。

カスタムアロケータが設定されない場合は、標準 C ライブラリの `malloc()`、`realloc()`、`free()` を使用する。`md_allocator_configure()` で設定したグローバル契約を、設定変更後の各操作に適用する。既存の document、ノード、切り離しフラグメントおよび関連する Markdown 出力も例外としない。出力バッファはライブラリが確保し、成功時に利用者へ渡し、専用の破棄操作で解放できるものとする。

設定変更前に確保されたメモリを新しいコールバックで扱えること、および設定変更と document 操作の同期は利用者が保証する。アロケータ設定は3つのコールバックをライブラリ内部へコピーして保持し、不正な設定や設定適用中の失敗では現在の設定を変更しない。`realloc` の失敗時は元のポインタを維持する。

### Consequences

* Good, because カスタムメモリアロケータを必要とする利用者や環境に対応できる。
* Good, because AST、切り離しフラグメントおよび関連出力を同じグローバル設定で扱える。
* Good, because document 作成・解析の通常 API にアロケータ引数を追加せずに済む。
* Bad, because 設定変更前に確保されたメモリを新しいアロケータで扱えることを利用者が保証する必要がある。
* Bad, because 利用者は、ライブラリが確保した出力を通常の `free()` で解放せず、専用の破棄操作を使用する必要がある。
