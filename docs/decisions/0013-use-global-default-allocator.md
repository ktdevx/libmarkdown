# グローバルアロケータを全 document から常時参照する

## Context and Problem Statement

libmarkdown はカスタムアロケータを利用できなければならない。一方、解析や document 作成のたびにアロケータを引数として渡すと、通常の呼び出しが複雑になる。利用者は処理の開始時にアロケータを設定し、その後の API では同じ設定を既定値として使えることを期待する。

グローバルなアロケータ設定の変更をいつ適用し、既存の document、切り離しフラグメントおよび出力の解放契約をどのように維持するかを決定する必要がある。

## Considered Options

* document 作成・解析ごとにアロケータを引数で渡す
* グローバル設定を禁止し、標準アロケータだけを既定値とする
* グローバル既定アロケータを設定し、document 作成時に契約をコピーする
* グローバルアロケータを全 document から常時参照する

## Decision Outcome

Chosen option: "グローバルアロケータを全 document から常時参照する", because 通常の API 呼び出しからアロケータ引数を除きながら、設定変更を既存の document とその関連オブジェクトにも適用できるため。

`md_allocator_configure()` は現在の既定アロケータを設定する。引数が NULL の場合は標準の `malloc()`、`realloc()`、`free()` を既定値とする。設定の変更はライブラリ側で禁止せず、変更後に作成済みを含む全 document、そこから生成されたノード、切り離しフラグメントおよび出力は、操作時点のグローバルアロケータを参照する。設定は3つのコールバックの値をライブラリ内部へコピーして保持し、不正な設定では現在の設定を変更しない。

利用者は設定対象のコールバックが必要な期間利用可能であることを保証する。複数スレッドからの設定変更と document 操作の同期も利用者の責任とする。設定変更前に確保されたメモリを後から解放する場合も、利用者は新しい設定がそのメモリを正しく扱えることを保証しなければならない。

### Consequences

* Good, because document 作成と解析の通常 API を簡潔にできる。
* Good, because 既存の document と出力にもアロケータ設定の変更を適用できる。
* Good, because 利用者は処理開始時にカスタムアロケータを一度設定できる。
* Bad, because グローバル設定はプロセス内の利用者とテストで共有される。
* Bad, because 設定変更と document 操作を同時に行う場合の同期を利用者が担う必要がある。
* Bad, because 設定変更後も既存の確保済みメモリを正しく解放できるよう、利用者がコールバックの互換性および寿命を管理する必要がある。
* Bad, because 同じプロセス内で独立したアロケータ設定を簡単に分離できない。
