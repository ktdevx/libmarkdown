# アロケータ設定変更時の責任境界を定義する

## Context and Problem Statement

libmarkdown は共通のグローバルアロケータを使用する。利用者が document、ノード、切り離しフラグメントまたは Markdown 出力を保持している間にアロケータを変更すると、変更前に確保されたメモリが変更後の `free` または `realloc` に渡される可能性がある。

アロケータの変更をライブラリ側で禁止または検出すると、ライブオブジェクトの追跡、アロケータ世代の保持、または document ごとの解放契約が必要になる。一方、利用者がアロケータを運用中に変更しないこと、および変更する場合の互換性を保証する責任境界を明確にすれば、グローバル設定の簡潔さを維持できる。

## Considered Options

* アロケータ設定の変更をライブラリ側で拒否する
* document または割り当てごとにアロケータを保持する
* アロケータ変更を許可し、安全性を利用者責任とする

## Decision Outcome

Chosen option: "アロケータ変更を許可し、安全性を利用者責任とする", because

* グローバルアロケータの簡潔な API を維持しながら、ライブオブジェクトの追跡や世代別アロケータ管理をライブラリへ追加せずに済む。
* カスタムアロケータは通常、アプリケーションの初期化時に設定され、運用中に頻繁に変更されるものではない。

`md_allocator_configure()` は任意の時点で呼び出せる。ライブラリは、既存の document、ノード、切り離しフラグメントまたは Markdown 出力が存在する状態での設定変更を拒否しない。設定変更後の各操作は操作時点のグローバルアロケータを参照する。

利用者は、次の条件を満たす責任を持つ。

* 設定変更と document、ノード、フラグメントおよび出力の操作を同期する
* 変更前に確保されたメモリを変更後の `free` および `realloc` が扱えることを保証する
* 設定したコールバックが必要な期間利用可能であることを保証する
* 複数スレッドからの設定変更とライブラリ操作を同期する

利用者がこの条件に違反した場合のメモリ破壊、解放失敗、未定義動作およびその他の結果は保証しない。ライブラリはアロケータ世代を追跡せず、旧アロケータによる自動解放も行わない。

### Consequences

* Good, because `md_allocator_configure()` の API を実行中の状態検査なしで簡潔に保てる。
* Good, because document ごとのアロケータ保持や割り当てごとの世代管理が不要になる。
* Good, because 利用者はアプリケーションの初期化時にアロケータを設定し、その後同じ設定を使い続けられる。
* Bad, because 利用者が設定変更と操作の同期を誤ると、ライブラリは安全性を回復できない。
* Bad, because 異なるアロケータを安全に併用する用途は、コールバック間の互換性を利用者が提供しない限り保証されない。
