# UTF-8 の妥当性を呼び出し側の前提条件とする

## Context and Problem Statement

libmarkdown の公開 API は UTF-8 の Markdown および文字列属性を扱う。UTF-8 の検証、正規化、置換および文字化けからの回復をライブラリで行うと、解析・編集・シリアライズの全経路に追加の処理と診断規則が必要になる。

不正な UTF-8 の入力をライブラリが検出して拒否するか、呼び出し側が UTF-8 の妥当性を保証するかを決定する必要がある。

## Considered Options

* ライブラリが UTF-8 を検証して不正な入力を拒否する
* 不正な UTF-8 を置換して処理を継続する
* UTF-8 の妥当性を呼び出し側の前提条件とする

## Decision Outcome

Chosen option: "UTF-8 の妥当性を呼び出し側の前提条件とする", because UTF-8 の Markdown を扱うライブラリとしての契約を保ちながら、文字エンコーディングの検証・補正を対象範囲から除外できるため。

解析入力、ノードのテキストおよび文字列属性、ならびにシリアライズ対象の AST は、有効な UTF-8 であることを呼び出し側が保証する。ライブラリは UTF-8 の妥当性を検証、正規化または補正しない。

この前提に違反する入力に対する解析結果、シリアライズ結果、診断および文字化けは保証しない。無効 UTF-8 は公開 API のエラーコードおよび診断の対象に含めない。

### Consequences

* Good, because 文字エンコーディングの検証コストと API 上の診断規則を持ち込まない。
* Good, because UTF-8 の Markdown を入力する通常の利用経路を単純に保てる。
* Bad, because 呼び出し側は文字列の UTF-8 妥当性を保証する責任を持つ。
* Bad, because 前提に違反した場合の文字化けや結果を利用者はライブラリに期待できない。
