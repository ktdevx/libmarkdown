# ADR 運用ガイド

本書では、libmarkdown プロジェクトにおける ADR の作成・記載・運用方法を定める。

## 1. ADR を残す目的

ADR（Architecture Decision Record）は、開発における重要な意思決定と、その理由を記録するための文書である。

ソースコードや設計書だけでは、現在の設計が「なぜそのようになっているのか」を判断できない場合がある。

ADR を残すことで、以下を将来確認できるようにする。

- どのような背景から意思決定を行ったか
- どのような案を検討したか
- なぜその案を採用したか
- どのようなトレードオフがあったか

ADR では、現在の設計を説明することだけでなく、**意思決定の経緯を残すこと**を重視する。

## 2. 作成の判断基準

以下のような意思決定を行った場合は、ADR の作成を検討する。

- 複数の設計案から 1 つを選択した
- ライブラリや外部仕様への対応方針を決定した
- API やデータ構造など、後から変更すると影響が大きい設計を決定した
- プロジェクト全体に影響する技術や方式を選択した
- 将来、選択理由を確認する可能性が高い決定を行った

一方、以下のような事項は、通常 ADR を作成する必要はない。

- 実装上の細かな判断
- コーディングスタイルなど、既存の規約に従うだけの判断
- 一時的な実装上の都合
- 具体的な API 仕様や実装詳細
- 局所的な AST の構造や属性の規則
- 既存の ADR や設計方針から明らかに導かれる判断

ADR は、すべての意思決定を記録するためのものではない。

**「後から、この決定をなぜしたのか確認したくなりそうか」**を 1 つの判断基準とする。

また、ADR を作成する場合でも、1 つの ADR に複数の独立した意思決定をまとめない。

複数の意思決定が含まれている場合は、ADR を分離するか、それぞれを要件・設計・API 仕様などの適切な文書に移す。

## 3. 記載内容

ADR には、以下の内容を記載する。

### 3.1 タイトル

タイトルには、意思決定の内容を簡潔に記述する。

```text
ADR-001: ADRに独自フォーマットを採用する
```

タイトルだけで、何について意思決定した ADR なのか分かることが望ましい。

### 3.2 ステータス

ADR の現在の状態を記述する。

```text
提案中
承認
廃止
置換 (ADR-NNN)
```

各ステータスは以下の意味を持つ。

- `提案中`: 意思決定を検討している状態
- `承認`: 意思決定が確定し、現在の方針として有効な状態
- `廃止`: 過去の意思決定が現在は適用されていない状態
- `置換 (ADR-NNN)`: 新しい ADR によって意思決定が変更された状態

`置換` の場合は、後継となる ADR を記載する。

### 3.3 背景

意思決定が必要になった状況、前提、経緯を記述する。

ここでは、**なぜ意思決定が必要になったのか**が分かることを重視する。

### 3.4 決定

採用する選択肢と、その決定理由を記述する。

```text
「{選択肢}」を採用する。

{決定理由}
```

決定理由には、必要に応じて以下の内容を含める。

- 選択肢間の比較
- トレードオフ
- 技術的な制約
- 将来の拡張性
- 保守性
- 既存コードとの整合性

具体的な API 仕様、データ構造の詳細、実装手順などは、必要に応じて要件・設計・API 仕様などの文書に記載する。

### 3.5 検討案

採用した案を含め、意思決定の対象となった選択肢を記録する。

各選択肢について、必要に応じて以下を記述する。

- 利点：その選択肢を採用することで得られる利点
- 欠点：その選択肢を採用した場合の問題や制約
- 中立：利点にも欠点にも該当しない事項

すべての項目を必ず記述する必要はない。

各項目は複数記載してよく、該当しない項目は省略する。

## 4. 運用

ADR はリポジトリ内で管理し、Git の履歴と Pull Request によって変更履歴を追跡できるようにする。

### 4.1 作成

ADR を新規作成する際は、[ADR テンプレート](../adr/template.md) を使用する。

ADR は `docs/adr/` に配置する。

```text
docs/
└── adr/
    ├── 001-title.md
    ├── 002-title.md
    ├── index.md
    └── template.md
```

ADR 番号は 3 桁のゼロ埋めされた連番とする。

ADR 作成時は、必ず [ADR 一覧](../adr/index.md) も更新する。

### 4.2 承認

ADR は、原則として Pull Request でレビューする。

レビューでは、以下を確認する。

**ADR としての適切性**

- ADR に残す価値のある意思決定か
- 後から選択理由を確認する際に役立つ内容か
- 要件・設計・API 仕様・規約などに記載すべき内容を ADR にしていないか
- 既存の ADR と重複していないか
- 1 つの ADR に複数の独立した意思決定を含めていないか
- 意思決定と具体的な仕様・実装詳細が不必要に混在していないか

ADR として適切でない場合は、無理に ADR として残さず、適切な文書への移動や ADR の分割を検討する。

**ADR の内容**

- 背景が十分に説明されているか
- 決定内容が明確か
- 決定理由が説明されているか
- 検討した案が適切に記録されているか
- 将来の開発者が読んでも意思決定の経緯を理解できるか
- 既存の ADR を置換する場合、置換対象の ADR が適切に指定されているか
- ADR 一覧が最新の状態になっているか

レビューでは、単に文章を整えるだけでなく、**その内容を ADR として残すこと自体が適切か**を確認する。

レビューを経て意思決定が確定したら、ADR のステータスを「承認」とする。

ADR の承認と実装の完了は別のものとして扱う。

ADR で方針を決定した後、その方針に基づく実装を別の Pull Request で行ってもよい。

### 4.3 変更

承認済みの ADR について、過去の意思決定そのものを書き換えて現在の状態に合わせることは避ける。

意思決定を変更する場合は、新しい ADR を作成する。

例えば、ADR で既に承認された方針を変更する場合は、以下の手順に従う。

1. 新しい ADR を作成する
2. 置換される ADR のステータスを「置換 (ADR-NNN)」に変更する

これにより、過去の意思決定と、その後の変更を Git の履歴と合わせて追跡できる。
