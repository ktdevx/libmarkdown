# ADR-010: 固定の CommonMark AST ノードモデルを使用する

## ステータス

承認

## 背景

libmarkdown は CommonMark Spec 0.31.2 のブロック要素とインライン要素を、利用者が編集可能な AST として公開する必要がある。

任意の属性マップだけを持つ汎用ノードでは、CommonMark の要素ごとに異なる親子関係、必須属性およびシリアライズ規則を一貫して検証することが難しい。

CommonMark の要素を固定されたノード種別として表現するか、属性マップを持つ汎用ノードとして表現するかを決定する必要がある。

## 決定

「固定の CommonMark ノード種別とノード固有属性を使用する」を採用する。

CommonMark の意味をノード種別として直接表現することで、ノードごとに必要な属性や親子関係を明確に定義でき、生成・編集・シリアライズにおける検証を一貫して行えるため。

## 検討案

### 固定の CommonMark ノード種別とノード固有属性を使用する

CommonMark の各要素をあらかじめ定義されたノード種別として表現し、要素ごとに必要な属性を持たせる方式。

- 利点: 親子関係と必須属性をノード種別ごとに明確に定義できる。
- 利点: AST が CommonMark の意味構造を直接表現できる。
- 利点: 対応するノード種別や属性を明確に定義できる。
- 欠点: 新しい構文に対応する場合、新しいノード種別や属性の追加が必要になる。
- 欠点: 汎用的な属性を自由に追加する用途には適さない。

### 属性マップを持つ汎用ノードを使用する

ノード種別を限定せず、属性マップなどの汎用的なデータ構造によって CommonMark の各要素を表現する方式。

- 利点: ノード種別や属性を柔軟に追加できる。
- 利点: CommonMark 以外の拡張構文にも対応しやすい。
- 欠点: ノード種別ごとの必須属性や親子関係を明確に定義することが難しい。
- 欠点: 属性名や属性値の妥当性を実行時に検証する必要がある。
- 欠点: 利用者が想定外の属性を持つノードを生成できる可能性がある。

### ブロックとインラインで別の AST 型を使用する

ブロック要素とインライン要素を異なる AST 型として定義し、それぞれ独立したデータ構造として扱う方式。

- 利点: ブロックとインラインそれぞれの構造を型として明確に表現できる。
- 利点: 不正なブロック・インライン間の関係を型レベルで制約しやすい。
- 欠点: AST 全体の操作 API が複雑になる。
- 欠点: ブロックとインラインをまたぐ共通の操作や走査を扱いにくい。
- 欠点: CommonMark の AST を単一の木構造として扱う場合に追加の抽象化が必要になる。
