# ADR-008: CommonMark フィクスチャを生成済み C データとして固定する

## ステータス

承認

## 背景

libmarkdown は CommonMark Spec 0.31.2 の公式 example を使用して適合性を検証する。

テスト実行時に仕様書をネットワークから取得すると、ネットワーク障害や取得先の変更によってテスト結果の再現性が失われる。また、仕様書全体をリポジトリに保持すると、テストに不要な仕様書本文まで管理する必要がある。

さらに、固定した CommonMark example を JSON や独自形式のテキストとして保持すると、テスト実行時にフィクスチャを解析する処理や追加のデータパーサーが必要になる。

CommonMark example をテストフィクスチャとしてどのように固定し、テストで利用するかを決定する必要がある。

## 決定

「CommonMark example を生成済み C データとしてテストフィクスチャに固定する」を採用する。

CommonMark Spec 0.31.2 から抽出した example をリポジトリに固定し、テストプログラムから直接利用できる C データとして保持することで、ネットワークや外部のデータパーサーに依存せず、再現可能な適合性テストを実行できるため。

## 検討案

### テスト実行時に CommonMark 仕様書をネットワークから取得する

テスト実行時に CommonMark 仕様書を取得し、そこから example を読み込んでテストする方式。

- 利点: 常に最新の仕様書を利用できる。
- 利点: フィクスチャをリポジトリで管理する必要がない。
- 欠点: ネットワーク環境に依存する。
- 欠点: 仕様書の取得先や内容の変更によってテスト結果が変化する可能性がある。

### CommonMark 仕様書全体をリポジトリに固定する

CommonMark Spec 0.31.2 の仕様書全体をリポジトリに保持し、そこから example を利用する方式。

- 利点: ネットワークに依存せず、特定の仕様バージョンを固定できる。
- 利点: 仕様書とテストフィクスチャの対応関係を保持しやすい。
- 欠点: テストに不要な仕様書本文まで管理する必要がある。
- 欠点: 仕様書全体をテスト実行時に扱うための処理が必要になる。

### 抽出した example を個別ファイルとして固定する

CommonMark Spec 0.31.2 から example を抽出し、Markdown と期待 HTML などを個別のファイルとしてリポジトリに保持する方式。

- 利点: フィクスチャの内容を人間が確認しやすい。
- 利点: 個々のテストデータの変更を確認しやすい。
- 欠点: 多数のフィクスチャファイルを管理する必要がある。
- 欠点: テスト実行時にファイルを読み込む処理が必要になる。

### 抽出した example を生成済み C データとして固定する

CommonMark Spec 0.31.2 から example を抽出し、テストプログラムから直接参照できる C データに変換してリポジトリに保持する方式。

- 利点: ネットワークに依存せず、再現可能なテストを実行できる。
- 利点: テスト実行時に追加のデータパーサーを必要としない。
- 利点: テストプログラムから入力と期待結果を直接利用できる。
- 欠点: 生成された C ファイルが大きくなる可能性がある。
- 欠点: フィクスチャの更新時に生成処理を実行する必要がある。
