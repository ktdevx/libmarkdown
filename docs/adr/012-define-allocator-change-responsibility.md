# ADR-012: アロケータ変更を許可し、安全性を利用者責任とする

## ステータス

承認

## 背景

libmarkdown は共通のグローバルアロケータを使用する。

利用者がライブオブジェクトを保持している状態でアロケータを変更すると、変更前に確保されたメモリを変更後のアロケータで解放または再確保する必要が生じる可能性がある。

この問題をライブラリ側で管理する場合、ライブオブジェクトの追跡やアロケータ世代の管理など、グローバルアロケータの仕組みが複雑になる。

グローバルアロケータの変更をライブラリ側で制限するか、変更を許可した上で利用者が安全性を管理するかを決定する必要がある。

## 決定

「アロケータ変更を許可し、安全性を利用者責任とする」を採用する。

グローバルアロケータの設定変更に伴うライブオブジェクトの追跡やアロケータ世代の管理をライブラリの責務とせず、アロケータの変更と既存オブジェクトの操作が安全に行われることを利用者の責任とすることで、グローバルアロケータの仕組みを簡潔に保てるため。

## 検討案

### アロケータ設定の変更をライブラリ側で拒否する

ライブオブジェクトが存在する間はアロケータの変更を拒否し、ライブラリ側で安全性を保証する方式。

- 利点: ライブオブジェクトとアロケータの不整合をライブラリ側で防止できる。
- 欠点: ライブオブジェクトの状態を追跡する必要がある。
- 欠点: アロケータ設定 API の実装が複雑になる。

### document または割り当てごとにアロケータを保持する

document または個々のメモリ割り当てに使用したアロケータを保持し、解放時にも同じアロケータを使用する方式。

- 利点: アロケータ変更後も既存のオブジェクトを安全に管理できる。
- 利点: 異なるアロケータを独立して使用できる。
- 欠点: document または割り当てごとにアロケータを管理する必要がある。
- 欠点: メモリ管理の実装および API が複雑になる。

### アロケータ変更を許可し、安全性を利用者責任とする

アロケータの変更をライブラリ側では制限せず、既存オブジェクトとの互換性や変更タイミングを利用者が管理する方式。

- 利点: グローバルアロケータの API を簡潔に保てる。
- 利点: ライブオブジェクトの追跡やアロケータ世代の管理が不要になる。
- 欠点: 利用者がアロケータの変更を適切に管理する必要がある。
- 欠点: 異なるアロケータを安全に併用するには、利用者側で互換性を保証する必要がある。
