# ADR-007: 状態コードと呼び出し側診断オブジェクトを返す

## ステータス

承認

## 背景

libmarkdown の解析、編集およびシリアライズでは、不正引数、メモリ不足、AST 不変条件違反などの失敗を利用者が識別できる形で報告する必要がある。

また、AST が生成されない解析失敗や、AST を持たないノード生成失敗にも同じエラー通知モデルを適用する必要がある。エラー情報をグローバル状態やスレッド局所状態に依存させず、各 API 呼び出しの結果として扱える方式を決定する必要がある。

## 決定

「状態コードと呼び出し側診断オブジェクトを返す」を採用する。

状態コードによって失敗の種別を明確に識別しつつ、必要に応じて呼び出し側が詳細な診断情報を取得できるため。また、AST の有無や共有状態に依存せず、解析、編集およびシリアライズで共通のエラー通知モデルを使用できるため。

## 検討案

### 状態コードだけを返す

API の戻り値として状態コードだけを返し、詳細なエラー情報は提供しない方式。

- 利点: API を単純にできる。
- 利点: エラー情報の所有権や寿命を考慮する必要がない。
- 欠点: 失敗した位置や処理段階などの詳細な情報を取得できない。
- 欠点: 利用者がエラー原因を特定しにくい場合がある。

### 状態コードと呼び出し側診断オブジェクトを返す

API の結果として状態コードを返し、必要に応じて呼び出し側が用意した診断オブジェクトへ詳細なエラー情報を格納する方式。

- 利点: 状態コードによる機械的なエラー判定と、詳細な診断情報の取得を両立できる。
- 利点: 診断情報を呼び出し側が管理できる。
- 利点: グローバル状態やスレッド局所状態に依存せず、API 呼び出し単位でエラー情報を扱える。
- 欠点: 診断情報を必要とする API では診断オブジェクトを扱うための API が必要になる。
- 欠点: 診断情報の内容やライフタイムなどについて API 契約を定義する必要がある。

### AST ごとの最終エラーを保持する

AST や document に最後に発生したエラー情報を保持し、利用者が後から取得する方式。

- 利点: エラー情報を取得するための引数を各 API に追加せずに済む。
- 利点: AST や document に関連するエラーをまとめて扱える。
- 欠点: AST が生成されない処理のエラーを保持する対象がない。
- 欠点: AST や document の状態とエラー情報のライフタイムを管理する必要がある。
- 欠点: 最後のエラーを保持するため、並行利用や複数の操作結果を扱いにくい。
