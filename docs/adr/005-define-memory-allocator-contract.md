# ADR-005: グローバルアロケータを採用する

## ステータス

承認

## 背景

libmarkdown は AST などの内部データを動的に確保する必要がある。

標準 C ライブラリのアロケータだけを使用する方式では、利用者が独自のメモリ管理方針を適用したり、標準アロケータを利用できない環境に対応したりすることが難しい。

一方、document ごとにアロケータを指定する方式では、公開 API や document の管理が複雑になる。

また、グローバルアロケータを採用する場合、設定変更によって既存のオブジェクトと使用するアロケータが異なる可能性がある。この問題をライブラリ側で管理すると、ライブオブジェクトの追跡やアロケータ世代の管理が必要になる。

アロケータをどの単位で管理し、設定変更をどのように扱うかを決定する必要がある。

## 決定

「グローバルアロケータを採用し、設定変更時の安全性を利用者責任とする」を採用する。

ライブラリ全体で共通のアロケータを設定することで、カスタムメモリアロケータに対応しながら、document 作成時などの API にアロケータ指定を追加せず、公開 API を簡潔にできるため。

また、アロケータの設定変更に伴うライブオブジェクトの追跡やアロケータ世代の管理をライブラリの責務とせず、既存オブジェクトとアロケータの整合性を利用者が管理することで、メモリ管理の仕組みを単純に保てるため。

## 検討案

### 標準 C ライブラリのアロケータだけを使用する

標準 C ライブラリのアロケータだけを使用し、カスタムアロケータには対応しない方式。

- 利点: 実装と API を単純にできる。
- 利点: アロケータの設定や管理が不要になる。
- 欠点: 利用者が独自のメモリ管理方針を適用できない。
- 欠点: 標準アロケータを利用できない環境への対応が難しい。

### document ごとにアロケータを指定する

document の生成時などにアロケータを指定し、document に関連するメモリをそのアロケータで管理する方式。

- 利点: document ごとに異なるアロケータを使用できる。
- 利点: アロケータ変更後も既存 document のメモリ管理を独立して維持できる。
- 欠点: document 作成 API などにアロケータ指定が必要になる。
- 欠点: 公開 API とメモリ管理の仕組みが複雑になる。

### グローバルアロケータを採用し、設定変更時の安全性を利用者責任とする

ライブラリ全体で共通のアロケータを使用し、設定変更そのものはライブラリ側で制限せず、既存オブジェクトとの互換性や変更タイミングを利用者が管理する方式。

- 利点: 公開 API を簡潔に保てる。
- 利点: ライブオブジェクトの追跡やアロケータ世代の管理が不要になる。
- 利点: カスタムメモリアロケータに対応できる。
- 欠点: 利用者がアロケータの変更を適切に管理する必要がある。
- 欠点: 異なるアロケータを安全に併用するには、利用者側で互換性を保証する必要がある。
